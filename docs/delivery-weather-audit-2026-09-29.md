## 대전 날씨 장애 원인

기존 순서는 Open-Meteo `kma_seamless` → 기상청 연결 프록시 → Open-Meteo 자동 모델이었다. 기상청 원 서버만 직접 호출하는 구조가 아니었다.

1. 현재 동일 좌표로 확인한 `kma_seamless`는 HTTP 200이지만 날짜별 기온·날씨 값이 모두 null이었다. [Open-Meteo 공식 안내](https://open-meteo.com/en/docs/kma-api)에도 KMA 모델 전환에 따른 데이터 업데이트 중단이 명시돼 있다.
2. 기상청 연결 프록시는 현재 조사에서 HTTP 500 `fetch failed` 또는 10초 읽기 제한 초과가 발생했다. 이는 프록시 경로 실패의 증거이며 기상청 전체 장애라는 뜻은 아니다.
3. 최종 대체 경로도 한 번만 호출하고, 모든 실패 원인을 기록하지 않았다. 대체 경로의 일시적 실패가 그대로 ‘수집 실패’로 표시될 수 있었다.
4. 날짜별 배열 길이가 다르면 기존 코드는 처리되지 않은 `IndexError`를 발생시킬 수 있었다. 회귀 테스트로 재현했다.

아침 준비 아티팩트에는 과천 12.2~24.1℃, 대전 수집 실패가 확인된다. 그러나 당시 마지막 Open-Meteo 자동 모델 호출의 상태 코드·예외 로그가 없어 그 실패를 429, 500, timeout 중 하나로 특정할 수 없다. 이번 점검 시에는 기존 코드도 자동 모델 경로로 두 도시 수집에 성공했다. 따라서 대전 좌표 오류나 매번 동일한 원인의 영구 장애라고 단정하지 않는다.

## 반영한 수정

- 중단된 `kma_seamless` 호출 제거. 기상청 프록시를 우선 시도하고 실패 시 기존 Open-Meteo 자동 모델로 전환한다.
- 자동 모델의 네트워크 오류·429·5xx에 최대 3회 시도. 일반 4xx는 반복하지 않는다. 숫자형 Retry-After를 따르되 5초를 초과하거나 해석하지 못하면 조기 재시도하지 않는다.
- 도시·제공자·HTTP 상태·예외 유형·재시도·최종 실패 로그를 추가했다. 인증 정보나 응답 본문은 기록하지 않는다.
- 요청 날짜, 필수 값 및 배열 길이를 검증하고 잘못된 응답은 안전하게 실패 처리한다.
- 응답 모델만 `weather_payloads.py`로 분리했다. 호출부 및 표시용 데이터 모델은 유지했다.
- 대체 예보는 Open-Meteo 자동 모델 결과이며 **기상청 단독 예보가 아니다**. 기상청 단독 사용이 필수라면 별도 원 API 연동과 인증 설정 검토가 필요하다.
